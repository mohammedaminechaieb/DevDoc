=== crewai_intro | overview | Crew ===
CrewAI is an open-source Python framework for orchestrating role-playing autonomous AI agents that collaborate to accomplish complex tasks. It models multi-agent systems as a crew of agents, each with a specific role, goal, and backstory, working together on a set of tasks. The core philosophy of CrewAI is to make multi-agent collaboration intuitive by borrowing from human team structures. An agent is like a team member with a job title (role), an objective (goal), and a character (backstory). Tasks are specific assignments with clear expected outputs. Tools are the capabilities agents use to interact with external systems. Install CrewAI with: pip install crewai crewai-tools. The framework integrates with OpenAI, Anthropic, Groq, and local Ollama models through LiteLLM. === crewai_process | process | Process ===
CrewAI supports two execution processes that determine how tasks are assigned and ordered within a crew: Sequential Process is the default. Tasks execute in the order they are defined in the tasks list. Each task's output is automatically passed as context to the next task. This is predictable, easy to debug, and suitable for linear pipelines. ```python crew = Crew( agents=[researcher, analyst, writer], tasks=[research_task, analysis_task, writing_task], process=Process.sequential, ) ``` Hierarchical Process uses a manager agent (or manager LLM) to autonomously coordinate the crew. The manager receives the overall goal, decides which agent should handle which aspect, delegates tasks, and aggregates results. This is more flexible for complex tasks where the optimal order is not known in advance. ```python crew = Crew( agents=[researcher, analyst, writer], tasks=[complex_task], process=Process.hierarchical, manager_llm=ChatOpenAI(model="gpt-4o"), verbose=True, ) ``` In hierarchical mode, the manager LLM acts as a coordinator. === crewai_memory | memory | Memory ===
CrewAI provides a memory system that allows agents to retain and retrieve information across tasks and runs. Memory in CrewAI has three tiers: short-term memory, long-term memory, and entity memory. Short-term memory stores recent interactions and reasoning steps within the current crew run. It is scoped to the execution context and cleared when the crew finishes. It helps agents maintain coherence across a multi-step task without re-reading the full history. Long-term memory persists across crew runs using a local vector database (ChromaDB by default). When an agent produces a significant finding or makes a decision, that is stored with a semantic embedding. In future runs, the agent can retrieve relevant past knowledge by similarity search. Entity memory specifically tracks entities mentioned during execution (people, organisations, locations, concepts) and stores structured facts about them. === crewai_tools | tools | BaseTool ===

=== crewai_flows | flows | Flow ===
CrewAI Flows is an advanced feature for building structured, event-driven AI pipelines with explicit control flow. While Crews orchestrate agents for open-ended tasks, Flows provide a code-first way to define exactly how data moves through a pipeline. Flows use Python decorators to define steps and their connections: ```python from crewai.flow.flow import Flow, listen, start, router class ContentPipeline(Flow): @start() def fetch_topic(self): return "quantum computing breakthroughs 2024" @listen(fetch_topic) def research(self, topic): # run research crew result = research_crew.kickoff(inputs={"topic": topic}) return result.raw @router(research) def route_by_quality(self, research_output): words = len(research_output.split()) if words > 500: return "write_article" else: return "expand_research" @listen("write_article") def write_article(self, research_output): result = writing_crew.kickoff(inputs={"research": research_output}) return result.raw @listen("expand_research") def expand_research(self, research_output): return research_output + " [expanded]" pipeline = ContentPipeline() result = pipeline.kickoff() ``` The @start() decorator marks the entry point of the flow. @listen(step) makes a method execute when the specified step completes. @router(step) makes a method act as a conditional branch

Flows have a shared state object (self.state) that persists across steps, similar to LangGraph's state. By default it is a simple dictionary. For structured state, a Pydantic BaseModel can be used as the state type. Flows support async execution with async def methods and asyncio.run() or await pipeline.kickoff_async(). Parallel execution is supported by listening to multiple events simultaneously. Flows are especially useful for content generation pipelines, data processing workflows, and integration scenarios where precise control over execution order is more important than agent autonomy.
