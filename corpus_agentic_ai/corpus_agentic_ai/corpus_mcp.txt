=== mcp_intro | overview | Protocol ===
The Model Context Protocol (MCP) is an open protocol developed by Anthropic that standardises how AI applications (hosts/clients) connect to external data sources and tools (servers). MCP provides a universal, vendor-neutral way to extend AI assistants with context from files, databases, APIs, and other systems. Before MCP, every AI application had to build custom integrations for each external service. MCP replaces this M×N integration problem with a standard protocol: M AI applications connect to N servers through a single, shared protocol. Any MCP-compatible client can use any MCP-compatible server. MCP is built on JSON-RPC 2.0. All messages — requests, responses, and notifications — follow the JSON-RPC 2.0 format. This makes MCP easy to implement in any programming language and easy to debug with standard HTTP/JSON tooling. === mcp_arch | architecture | Host,Client,Server ===
MCP defines a three-role architecture: Hosts, Clients, and Servers. Hosts are AI applications that want to use MCP servers. Examples include Claude Desktop, Cursor IDE, and custom AI chatbot applications. The host is responsible for managing the lifecycle of MCP connections, coordinating client-server interactions, and presenting server capabilities to the AI model. Clients are protocol clients that live inside the host application. Each client manages exactly one connection to one server. The host creates and manages client instances. Clients handle protocol-level concerns like capability negotiation, message serialisation, and transport management. Servers are lightweight services that expose specific capabilities through the MCP protocol. A server exposes one or more of the four primitives: Tools (functions the AI can call), Resources (data the AI can read), Prompts (prompt templates), and Sampling (the ability to request LLM completions). Communication flow: The host creates a client for each server it wants to connect to.

=== mcp_tools | tools | Tool ===
MCP Tools are the most commonly used primitive. They allow an AI model to perform actions: calling APIs, running queries, executing code, interacting with file systems. Tools are the equivalent of function calling in OpenAI's API. A tool is defined by its name, description, and input schema (JSON Schema). When an AI model calls a tool, MCP routes the call to the server, which executes the tool function and returns the result. === mcp_resources | resources | Resource ===
MCP Resources allow servers to expose data that the AI model can read. Resources are identified by URI, can be listed, subscribed to for updates, and read on demand. They are analogous to files in a file system, but can represent any addressable data. Resources are distinct from tools: resources are data that the AI reads passively; tools are actions that the AI executes actively with side effects. Reading a resource is always safe; calling a tool may have side effects. Resource types: Static resources have a fixed URI and content. Dynamic resources generate content on demand (e.g., a resource for the current date/time). Template resources use URI templates with parameters (e.g., file:///{path} where path is provided by the client). === mcp_prompts | prompts | Prompt ===
MCP Prompts allow servers to expose reusable prompt templates that hosts can present to users and AI models. Unlike tools (which execute actions) and resources (which expose data), prompts are pre-crafted instructions and conversation starters. Prompts can be parameterised, allowing the host to fill in template variables before presenting the prompt. They can reference server resources, allowing the prompt to include dynamic data from the server. === mcp_sampling | sampling | Sampling ===
MCP Sampling is a protocol primitive that allows MCP servers to request LLM completions through the host, without having direct access to an LLM API. This is a unique capability that inverts the usual flow: instead of the AI model calling a server, the server can ask the AI model to generate text. Sampling enables powerful server-side AI workflows: a server can request the LLM to summarise retrieved documents, classify incoming data, or generate descriptions for resources — all without having its own API key or LLM configuration. The sampling flow: (1) The server sends a sampling/createMessage request through the existing MCP connection. (2) The host receives the request and can inspect it. (3) If approved (by the user or by policy), the host forwards it to the AI model. (4) The AI model's response is sent back to the server. This architecture keeps the user in control: the host
