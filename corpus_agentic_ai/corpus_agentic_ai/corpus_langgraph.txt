=== lg_intro | overview | StateGraph ===
LangGraph is a low-level orchestration framework for building stateful, multi-step, and multi-agent AI applications with large language models. It extends LangChain's ecosystem but introduces an explicit graph-based execution model where nodes represent computation units and edges represent transitions between them. At its core, LangGraph encodes application logic as a directed graph. Each node in the graph is a Python function that accepts the current application state and returns state updates. Edges define which node runs next, and they can be conditional — routing to different nodes based on the current state content. This model gives developers explicit control over the flow of information through an AI system. LangGraph is especially well-suited for agentic workflows that require: (1) cycles and loops, where the agent must revisit a decision; (2) persistence across steps, where intermediate results must be stored; (3) human-in-the-loop intervention, where a person can review or override an agent decision;

=== lg_concepts | concepts | State,Nodes,Edges ===
LangGraph's execution model is built around three primitives: State, Nodes, and Edges. Understanding these three abstractions is essential for building correct LangGraph applications. State is the shared data structure that every node reads from and writes to. It is defined once at graph construction time as a TypedDict (or Pydantic model) and persists across all nodes in the graph. When a node returns a dict, LangGraph merges it into the current state using reducers. The default reducer for a field is overwrite — the returned value replaces the existing value. For list fields that should accumulate (like a messages history), developers annotate the field with a custom reducer using Python's Annotated type: ```python from typing import Annotated from langgraph.graph.message import add_messages class MyState(TypedDict): messages: Annotated[list, add_messages] counter: int # default overwrite reducer ``` Nodes are Python functions (sync or async) with the signature (state: StateType) -> dict. === lg_persistence | persistence | Checkpointer ===
LangGraph's persistence layer, called the checkpointer, allows graph state to be saved and restored across runs, sessions, or failures. Without a checkpointer, each invoke() call starts from scratch. With a checkpointer, state is stored after every step and can be resumed from any point. The checkpointer is attached at compile time: ```python from langgraph.checkpoint.memory import MemorySaver from langgraph.checkpoint.sqlite import SqliteSaver # In-memory checkpointer (development / testing) memory = MemorySaver() app = graph.compile(checkpointer=memory) # SQLite checkpointer (single-process production) db_path = "/tmp/langgraph_state.db" with SqliteSaver.from_conn_string(db_path) as checkpointer: app = graph.compile(checkpointer=checkpointer) ``` Each invocation is associated with a thread_id that acts as a session identifier. When you invoke the graph, you pass a config dict with the thread_id: ```python config = {"configurable": {"thread_id": "user-session-42"}} result = app.invoke(input_state, config=config) ``` Subsequent invocations with the same thread_id resume from the last saved checkpoint. This enables multi-turn conversations where the agent remembers previous context. Checkpointers expose several

LangGraph Cloud uses a managed PostgreSQL checkpointer transparently. The persistence layer also powers time-travel debugging. By replaying from an earlier checkpoint, developers can test alternative code paths without re-running expensive LLM calls, or investigate why an agent took a wrong turn.

=== lg_multi_agent | multi_agent | Supervisor,Swarm ===
LangGraph supports multi-agent architectures through two primary patterns: the Supervisor pattern and the Swarm (handoff) pattern. In the Supervisor pattern, a central orchestrator agent routes work to specialized sub-agents. The supervisor receives the user request, decides which agent to call, invokes it, and continues until the task is complete. Each specialist agent is itself a compiled LangGraph graph, invoked as a node inside the supervisor graph. ```python from langgraph.graph import StateGraph, MessagesState, END from langgraph_supervisor import create_supervisor # community package # Define specialized agents researcher = create_react_agent(llm, tools=[search_tool], name="researcher") writer = create_react_agent(llm, tools=[write_tool], name="writer") # Create supervisor supervisor = create_supervisor( agents=[researcher, writer], model=llm, prompt="Route tasks to researcher or writer based on the request type." ) app = supervisor.compile() ``` In the Swarm pattern (network of agents), there is no central supervisor. === lg_tools | tools | ToolNode ===
LangGraph integrates tightly with LangChain's tool ecosystem. Tools in LangGraph are defined using the @tool decorator or by subclassing BaseTool, and they are bound to an LLM using model.bind_tools(tools). The ToolNode prebuilt component handles the execution of tool calls returned by an LLM. It inspects the last AI message in the state for tool_calls, executes each tool function in sequence (or in parallel if configured), and returns a list of ToolMessage objects. === lg_human_loop | human_in_the_loop | Interrupt ===
Human-in-the-loop (HITL) is one of LangGraph's most important features for production applications. It allows a graph to pause at designated points, present the current state to a human reviewer, receive edits or approvals, and resume execution. Interrupts are configured at compile time using the interrupt_before and interrupt_after parameters: ```python app = graph.compile( checkpointer=MemorySaver(), interrupt_before=["action_node"], # pause BEFORE this node runs ) ``` When the graph reaches the interrupt point, execution pauses and invoke() (or stream()) returns the current state. The calling code can then inspect the state, optionally modify it using update_state(), and resume execution by calling invoke() again with the same thread_id: ```python config = {"configurable": {"thread_id": "review-session-1"}} # First run — pauses before action_node state = app.invoke(initial_input, config=config) print("Agent wants to:", state["proposed_action"]) # Human reviews and approves (or modifies the state) app.update_state(config, {"approved": True}) # Resume execution from the checkpoint final_state = app.invoke(None, config=config) ``` The None input

=== lg_streaming | streaming | stream,astream ===
LangGraph supports three streaming modes, controlled by the stream_mode parameter: 1. "values" mode streams the full state after each node completes. This is the default and most common mode for applications that want to display the current agent state at each step. 2. "updates" mode streams only the diff (the dict returned by each node). This is more efficient when the state is large and only a few fields change per step. 3. "debug" mode streams all internal events including edge decisions, checkpoint saves, and node start/end events. Useful for debugging complex graphs. ```python # Stream state values after each step for state in app.stream(input, stream_mode="values"): print(state["messages"][-1]) # Stream only the updates for update in app.stream(input, stream_mode="updates"): print(update) # e.g. {"agent": {"messages": [AIMessage(...)]}} ``` For token-level streaming (seeing LLM output as it generates), use the asynchronous astream_events() API, which surfaces fine-grained events from inside nodes: ```python async for event in
